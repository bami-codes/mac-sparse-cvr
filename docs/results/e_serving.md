# 서빙: 원시 입력에서 보정된 전환 확률까지

- 요청 하나(사용자 1명, 광고 후보 100개)를 CPU 코어 하나로 점수화하는 데 BASE는 p50 1.89ms·p99 3.21ms, MoAE는 p50 3.98ms·p99 5.64ms가 걸린다(Linux 서버, AMD EPYC 4565P).
- 사용자 특성과 구매 이력을 후보마다 다시 인코딩하지 않고 요청마다 한 번만 인코딩한다. 그러면 요청 p50이 BASE 34%, MoAE 20% 줄고, 결과 확률은 그대로다.
- 서빙한 확률은 평가에 쓴 예측과 같다.

## 경로

원시 행 → 공식 어휘로 코드 변환(`utils.data.df_to_dict`와 같은 조회) → 공식 텐서 배치(`MALDataset`과 같음) → 모델 → 공통 보정 (ii) 또는 그룹별 축소 보정 (iii).

- 모델은 연구 E의 `train-17` 체크포인트(시드 2026)와 그 보정기 (iii)다. `train-19` 모델은 구조와 텐서 크기가 같다.
- 코드는 [cvr/serving_e.py](../../cvr/serving_e.py)다.
  - `ServerE.predict(rows)`: 행마다 그 행의 사용자 정보를 쓴다.
  - `ServerE.predict_request(user_row, candidates)`: 한 사용자의 후보들을 한 번에 점수화한다.
- 후보별 이미지·텍스트 유사도(`mm_feat0_seq`, `mm_feat1_seq`)는 MAC에 미리 계산된 값을 읽는다.

## 정확성

| 확인 | BASE | MoAE | 기준 |
|---|---|---|---|
| 한 행씩 서빙한 원시 확률 vs 평가 예측 (V2 2,999행, 희소 그룹 1,195행 포함) | 2.7e-7 | 1.8e-6 | 1e-5 |
| 같은 행을 배치로 서빙한 원시 확률 vs 평가 예측 | 1.0e-7 | 2.1e-7 | 1e-6 |
| 보정 확률 vs 평가 예측에 같은 보정기를 적용한 값 | 2.9e-7 | 1.6e-6 | 1e-5 |
| 공유 인코딩 vs 후보마다 인코딩 (요청 320개) | 0 | 0 | 1e-6 |

- 최대 절대 차이다.
- 평가 예측은 다른 CPU(Apple M4)에서 배치로 계산했다. 한 행씩 계산하면 x86에서 배치 크기 1의 float32 반올림이 달라진다. 그래서 MoAE의 한 행이 1.8e-6까지 차이 났다. 같은 배치 경로로 비교하면 2.1e-7 안이다.

## 신규 입력

테스트: `uv run pytest -q tests/test_pymal_run.py -k serving`

| 입력 | 동작 |
|---|---|
| 처음 보는 `user_id` | 조회하지 않는다. 공식 모델은 이 열을 쓰지 않는다(`user_indices[:, 1:]`). |
| 어휘에 없는 값 (새 광고·상점·이력 상품) | 그 어휘의 결측값(PAD)으로 바꾸고, 열별로 센다(`ServerE.oov`). |
| 학습 통계에 없는 광고 그룹 (`ad_feat1`) | 보정기의 미관측 그룹 계수를 쓴다. 이 계수는 보정 적합 자료의 미관측 행으로 맞췄다. 평가와 같은 동작이다. |

## 지연

**환경**

- Linux 서버 1대(RunPod CPU 포드, AMD EPYC 4565P), PyTorch 2.15.0, Python 3.11이다.
- 프로세스를 CPU 하나에 고정했고, PyTorch 스레드는 1개다. 고정한 CPU와 하이퍼스레드 짝은 모두 이 컨테이너에 배정된 것이다.
- 네트워크, 요청 파싱, 피처 저장소 조회, 유사도 계산은 시간에 넣지 않았다.

**측정**

- 세션은 세 개이고, 20분 간격이다. 세션마다 모델별로 클릭 10,000건과 요청 6,000개(두 경로에 3,000개씩)를 잰다.
- 경로별 요청 p99는 세션마다 요청 3,000개 중 가장 느린 30개 부근의 값이다. 그래서 p99의 구간은 p50보다 넓다.
- 요청마다 다른 사용자를 쓰고, 후보 100개는 V2 행 20,000개에서 뽑는다. 요청은 V2의 실제 행으로 만든 합성 요청이다.
- 모델은 블록 단위로 ABBA 순서로 번갈아 잰다. 두 경로는 블록 안에서 요청마다 번갈아 잰다.
- 구간은 블록 단위 부트스트랩으로 구했다. 측정 규약은 [DESIGN.md](../DESIGN.md)의 §18.12.1에 있다.
- 기록: [records/serving_summary_linux.json](records/serving_summary_linux.json), 일치 검사 [records/serving_check_linux.json](records/serving_check_linux.json). 측정 코드는 커밋 `a15ffd4`의 파일과 해시가 같다.

## 읽는 법

- **단축된 곳.** 후보마다 인코딩하면 요청 시간의 가장 큰 몫이 인코딩이다. 같은 사용자의 구매 이력을 후보 수만큼 반복해서 어휘 코드로 바꾸기 때문이다. 공유 인코딩은 이 단계를 1.69ms에서 0.77ms로 줄였다. 모델 계산과 보정은 그대로다.
- **다음 병목.**
  - BASE는 공유 인코딩 뒤에도 요청 시간의 약 40%가 인코딩이다. 남은 몫은 후보마다의 광고 특성 조회와 텐서 생성이다. 피처 저장소가 정수 코드를 주거나 조회를 벡터화하면 더 줄일 수 있다(재지 않았다).
  - MoAE는 요청 시간의 77%가 모델 계산이다. 모델 계산이 BASE의 약 2.9배라서, 더 줄이려면 모델 쪽을 바꿔야 한다.
- **보정 비용.** 그룹별 보정은 후보 100개에 p50 0.07–0.09ms다.
- **모델 선택.** 순위 성능과 확률 품질의 비교는 [공식 테스트 결과](e_final_test.md)에 있다. 이 표는 그 선택의 지연 비용이다. 요청당 MoAE는 BASE보다 p50 2.1ms, p99 2.4ms 더 걸린다.

## 재현

```bash
uv run pytest -q tests/test_pymal_run.py -k serving              # 원자료 없이: 공식 텐서 배치, 신규 입력, 공유 인코딩
PYTHONPATH=. uv run python scripts/serving_e.py prepare           # 측정 행과 평가 예측을 한 번 고정 (V2와 평가 예측 필요)
bash scripts/serving_sessions.sh linux                            # 측정할 서버에서: 일치 검사, 20분 간격 세션 3개, 요약
PYTHONPATH=. uv run python scripts/serving_e.py render linux      # 위 표
```

서버에는 `runs/e_study/serving_v3/`의 행·계획 파일, 체크포인트 2개와 실행 기록, 보정기 2개, 그룹 통계를 복사한다. 어휘는 `python3 scripts/fetch_mac.py vocabs`로 받는다.
